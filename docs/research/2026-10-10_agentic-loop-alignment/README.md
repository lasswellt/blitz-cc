# Harden blitz's gates before adding agents

Blitz's core design already matches the evidence: a JSON task DAG that only a script can write, per-task `verify[]` commands, fresh-context subagents, a Stop-hook gate and a separate critic. Anthropic's guidance, the long-running-harness literature and the best-measured anti-cheating results all point to this design. The next release should therefore close gaps in enforcement rather than add orchestration. Five changes matter most. First, blitz's guard hooks fail open today; Claude Code 2.1.295 added `onFailure: "block"`, which lets them fail closed. Second, 3.10.0 passes the Agent tool's `effort` parameter on every spawn, a 2.1.292 feature, while `cc_min` still says 2.1.271. Third, 3.10.0 runs Haiku 5.5 at `low` for multi-step web retrieval, and Anthropic documents that this setting skips searches and stops early. Fourth, the opt-in cross-model critic panel lets any single REJECT block, even though cross-model reviewers have roughly 30% precision. Fifth, `next --loop` has per-task circuit breakers but no cross-tick check for "no progress". Most other 3.10.0 choices hold up: the 5.5 price table, Sonnet at `medium` for implementation, Opus for the reject verdict, and keeping agent teams off by default. The recommendations below are ranked P0 (do now), P1 (next minor release) and P2 (when there is capacity). Each gives an effort estimate (S is under half a day, M is one to two days, L is three days or more) and the files it touches.

Equally important is what blitz should **not** do. It should not make agent teams a default. It should not raise Sonnet's effort to `xhigh` or `max` for stuck rounds. It should not count prompt-level "don't cheat" instructions as a control. It should not remove the critic because of Anthropic's anti-verification guidance for Opus 5. The sections below give the evidence for each item.

## 3.10.0 mostly holds up, but two choices need correcting

The **model table is correct**. Opus 5.5 lists at $4/$20 with $0.20 cache reads, Sonnet 5.5 at $2/$10 with $0.10 cache reads after the post-launch cut, and Haiku 5.5 at $0.10/$0.50, rising to $0.50/$2.50 once a prompt passes 100K tokens ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Anthropic: Haiku 5.5](https://www.anthropic.com/claude-haiku-5-5)). The decision to **pin Sonnet lanes at `medium`** is also well supported. Sonnet 5.5 defaults to `high`, and Anthropic's advice for agentic coding is to "start with `medium` for well-specified tasks and move to `high` for harder or longer ones" ([Effort docs](https://platform.claude.com/docs/en/build-with-claude/effort)). Without a per-spawn setting, every `dev` would have run a level above that advice.

The concern that **Sonnet at high effort costs more than Opus** does not apply to blitz, and it reinforces 3.10.0's escalation path. Artificial Analysis measured Sonnet 5.5 using about 60% more output tokens than Opus 5.5 at max effort, which put Sonnet at **$7.60 per task against $5.98 for Opus** ([OODA Loop](https://oodaloop.com/briefs/technology/claude-sonnet-5-5-reaches-2-on-artificial-analysis-index-but-uses-more-tokens/)). Anthropic adds that at `xhigh` and `max`, Sonnet 5.5 "can start its own rounds of review and verification, sometimes with subagents" ([Prompting Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). Blitz never raises Sonnet past `medium`; it moves fix rounds 4–5 to Opus at `high`. That is the cheaper and stronger route, so it should stay. The AA figures are second-hand, because AA's own pages were unreachable.

The **Opus `high` setting for the reject critic is defensible but unproven**. Opus 5.5 now defaults to `medium`, and Anthropic says `medium` "matches or exceeds Claude Opus 5 at `high` on coding and knowledge-work evaluations" ([Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). Blitz's `high` is therefore one level above a default that is already strong. Keep it for plan-scope and ship verdicts, and let recommendation 6 test `medium` on small diffs. No public per-effort quality curves exist for any 5.5 model, so blitz's own evals have to settle this.

The first choice the evidence contradicts is **Haiku 5.5 at `low` for retrieval**. Anthropic's Haiku guidance is explicit: "In long agent prompts, the model is more likely to skip a search, stop early, or skip a check at low." It recommends `medium` "for most work, including agentic coding" ([Effort docs](https://platform.claude.com/docs/en/build-with-claude/effort)). Moving from low to medium "roughly halved early stopping". It also "more than doubled the output tokens", and Haiku "sometimes needs a nudge to search, most at low effort", so Anthropic suggests giving it today's date ([Prompting Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)). Blitz's `library-docs`, `web-researcher` and `infra-analyst` are multi-step search agents, which is the documented failure case. Doubling the output of a model that costs one-twentieth of Sonnet costs little. The `det-*` collectors and `next` row triage are single-shot bookkeeping, so they should stay at `low`. Every Haiku lane also needs its prompt kept under 100K tokens, where the price steps up 5x.

The second contradicted choice is the **agent-teams naming scheme**. The docs say Claude "launches a teammate when it calls the Agent tool with a `name` while agent teams are enabled, unless the call is a fork or passes `isolation` on the call itself" ([Agent teams](https://code.claude.com/docs/en/agent-teams)). Blitz's parallel path passes `isolation: "worktree"` together with `name: "dev-<ID>"`, so it escapes. The **sequential path in `skills/build/references/main.md` (line 311) passes `name` without `isolation`**. With the experimental flag on, each sequential `dev` becomes a teammate. The definition's `skills` preload then does not apply ("Claude Code doesn't apply the definition's `skills` to a teammate"), and in-process teammates cannot be resumed.

The rationale in 3.10.0's §1.5 is also partly wrong. It presents `name` as a teams feature that enables `SendMessage(to: "dev-<ID>")`. The sub-agents page says "`SendMessage` doesn't require agent teams to be enabled", and that a completed named subagent "resumes in the background without a new `Agent` invocation" ([Sub-agents](https://code.claude.com/docs/en/sub-agents)). Blitz should keep `name` everywhere, because it is what makes fix-round resume work without teams. It should also do one of two things on the sequential path when `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`: omit `name`, or warn at SessionStart. §1.5 should then say that names serve resume and visibility, not teams.

The third issue is not a model choice but a **floor mismatch**. Every 3.10.0 spawn passes the Agent tool's `effort` parameter, which arrived in 2.1.292 ([CL 2.1.292](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)), yet `compat.json` keeps `cc_min` at 2.1.271. The notes do not establish whether an older client rejects the unknown parameter or silently ignores it. Either way, the declared floor is false. Raising it to **2.1.296** also brings in several fixes:

- In 2.1.288, PreToolUse hooks that failed matching or serialization now block instead of being skipped, and plugin agents spawned by name keep their own prompt, tools and effort.
- In 2.1.290, resumed subagents keep their thinking and prompt cache.
- 2.1.295 adds `onFailure: "block"` and the 32-skill preload cap.
- 2.1.296 adds `autoCompactWindow` and `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL`.

All of these are in the [changelog](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md). The fourth issue is minor. **Doctor D-318**, which warns when `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` flattens per-agent routing, is well aimed, because that variable silently moves the opus/high critic stage of `review-fanout.js` onto whatever model the operator set ([Workflows](https://code.claude.com/docs/en/workflows)).

## Blitz's guards fail open, and 2.1.295 can close them

Claude Code's hook contract is permissive by default. Exit 2 blocks, but "any other exit code, crash, or can't start" is a non-blocking error after which "the action proceeds". A PreToolUse hook that times out does not block either ([Hooks](https://code.claude.com/docs/en/hooks)). None of blitz's hook entries in `hooks/hooks.json` sets `onFailure`. A local read of `block-destructive-sql.sh` shows the pattern the security notes flagged: it parses input with `jq … 2>/dev/null || echo ""` and then runs `[[ -z "$CMD" ]] && exit 0`. **If `jq` is missing or the input is malformed, the guard allows everything.**

Since 2.1.295, `"onFailure": "block"` on command and HTTP hooks makes a hook that "can't start, times out, or exits with an unexpected code" block "instead of letting it through" ([CL 2.1.295](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)). Recommendation 2 applies that key to every enforcement PreToolUse entry: `kill-switch`, both `tasks-guard` matchers, `pre-edit-guard`, `block-test-deletion`, `block-test-disabling`, `block-as-any-insertion`, `block-no-verify`, `block-destructive-git` and `block-destructive-sql`. Each script should also treat a parse failure as exit 2 with a reason. `startup-validate.sh` should refuse loudly when `jq` is absent. Advisory hooks (format, telemetry, heartbeat, context injection) should stay fail-open so that a broken helper does not lock up a session. The key "has no effect on `Stop`, `SubagentStop`, `TaskCompleted`, `TeammateIdle`, or background hooks" ([Hooks](https://code.claude.com/docs/en/hooks)). `stop-gate.sh` must therefore keep handling its own errors.

These guards are one layer of defense among several, not a boundary. Since 2.1.283–2.1.285, auto mode is the default permission mode in most sessions. Its classifier already blocks force pushes, `git reset --hard`, secrets leaving the repo and "commenting out security-guarding tests" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Anthropic also warns that matching on command text misses `sh -c`, variables and path variants ([Permissions](https://code.claude.com/docs/en/permissions)). On top of that, a user-installed mod handling `tool.check` "can approve a call that a deny rule refuses" outside managed or Team/Enterprise setups. Mods are stopped by `disableAllHooks`, `--bare` and `--safe-mode` ([Mods admin](https://code.claude.com/docs/en/plugins/mods/admin); [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)). Blitz's documentation should therefore describe its guards as deterministic defense-in-depth. It should recommend a hardened profile: sandbox on, `failIfUnavailable`, `allowUnsandboxedCommands: false`, and `blockReadsOutsideWorkingDirectories` ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). It should also say plainly that Windows needs Git Bash or WSL2, because a bash hook that "can't start" fails open.

The external critic deserves specific attention because it fits the "lethal trifecta": private data, untrusted content and an outbound channel ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). `critic-external.sh` already does the right things on permissions. Codex runs under `--sandbox read-only`, Copilot runs without `--allow-all-tools`, and agy gets an allow-list rather than `--dangerously-skip-permissions`. These choices match the auto-mode classifier's rule against third-party agent loops that run with approvals disabled ([Permission modes](https://code.claude.com/docs/en/permission-modes)). What is missing is any check on what leaves the machine. The diff is sent to vendor clouds with no secret scan. Recommendation 5 adds a gitleaks-style scan, or blitz's existing secret regexes, with redaction of `.env`-like hunks before any provider call. It also adds a bats assertion that no `--yolo`, `--dangerously-*` or `--yes-always` flag ever appears.

The supply-chain record supports blitz's current posture and argues for writing it down. Plugin4Shell let a non-GitHub marketplace swap code behind a commit pin; it was fixed in 2.1.179 ([hard2bit](https://hard2bit.com/en/blog/plugin4shell-commit-pinning-bypass-ai-coding-agent-plugins-claude-code-codex-copilot-gemini/)). Snyk found critical issues in **13.4% of about 4,000 public skills** ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)). A P2 `SECURITY.md` should state that installing blitz means trusting its bash hooks with the user's privileges. It should map the TB-1 to TB-5 trust boundaries to the OWASP ASI items (supply chain, memory poisoning through `.cc-sessions/`, inter-agent channels) and pin the marketplace to GitHub.

## The critic is the right idea with the wrong veto rules

The case for a separate critic is strong. Anthropic found that "separating the agent doing the work from the agent judging it proves to be a strong lever", and that tuning a standalone evaluator to be skeptical is "far more tractable" than self-critique ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). In a 900-session planted-error study, fresh-context same-model review beat self-review and led on code, with F1 of 40.7 against 37.2 for a top-tier cross-model reviewer ([arXiv 2610.01471](https://arxiv.org/html/2610.01471v2)). That supports blitz's read-only `critic` with `omitClaudeMd`.

The critic should stay, despite the guidance that seems to argue against it. Anthropic's Opus 5 prompting page says to remove "use a subagent to verify" instructions, because they "cause over-verification" ([Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)). That advice targets verification steps placed in the working model's own prompt. Blitz's critic is a harness gate on a diff written by a Sonnet `dev`, which is the writer-verifier pattern the same page praises. The evidence does argue against running the critic at full strength on every diff. The harness-design author found the evaluator "worth the cost when the task sits beyond what the current model does reliably solo". A LiveCodeBench study found that Claude reviewing Claude changed the pass rate by **+0.0 pp at roughly double the cost** ([arXiv 2607.21656](https://arxiv.org/html/2607.21656v1)). Anthropic's Code Review finds issues in only **31% of sub-50-line PRs, against 84% of PRs over 1,000 lines** ([InfoQ](https://infoq.com/news/2026/04/claude-code-review)). Recommendation 6 therefore keeps the critic mandatory but scales its effort. Plan-scope and `ship` verdicts stay at Opus `high`. Small diffs that are entirely green on deterministic checks run Opus at its `medium` default. Blitz's own evals then confirm the switch does not raise false LGTMs.

The **"only high severity" concern** applies to blitz in a subtler form. Opus 5 may take a prompt saying "only report high-severity issues" literally; Anthropic says to "ask it to report everything and filter in a separate pass instead" ([Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)). Blitz's survey mode limits findings to "correctness and stated requirements". That matches Anthropic's best-practices wording for avoiding over-engineering ([Best practices](https://code.claude.com/docs/en/best-practices)), so it should stay. The reject mode is the problem. `agents/critic.md` frames it as "find ONE reason to reject". A literal-minded Opus can stop at the first hit, which leaves the fix loop to find the remaining defects one round at a time, and every round costs a full Opus spawn. The fix is to have the critic list every candidate with evidence and confidence, keep the existing FP-verify step, and derive LGTM or REJECT with a `jq` filter over registry authority. `check` already treats the reply as JSON, so this is mostly a prompt and filter change. Where `check`'s "precision-biased, low-confidence advisory findings are suppressed" behavior lives in a prompt, it should move into that filter.

The **cross-model panel's "any REJECT blocks" rule** is the riskiest policy in the stack. The best cross-model reviewer in the planted-error study reached only **28.6% precision and 32.3% F1**, and about 9.4% of its false positives were "model bias" errors such as flagging Claude-specific tools as nonexistent ([arXiv 2610.01471](https://arxiv.org/html/2610.01471v2)). Cross-model review still has value: pairing one same-model and one cross-model reviewer lifted union recall to **56.7%, against 42.7%** for two same-model reviews. The industry pattern that achieves low false-positive rates is to find broadly, then verify each finding in a separate pass. Anthropic's Code Review reports fewer than 1% of findings marked incorrect this way ([Code Review](https://claude.com/blog/code-review)), although no one has validated that figure independently. Blitz should keep external providers as a source of recall, but route their REJECTs through the critic's existing FP-verify rule. A REJECT backed by a reproducing command, a failing test, or confirmation by the in-Claude critic blocks. Anything else becomes a parked concern. The same reasoning applies to the refuter panels: same-model refuters are correlated, and debate does not beat self-consistency at matched compute ([arXiv 2502.08788](https://arxiv.org/abs/2502.08788v2)). Persona variety should therefore not count as independent votes (P2).

On test gaming, blitz's existing hooks are its best-evidenced feature. ImpossibleBench found that **over 79% of Claude's cheats modify tests**, and read-only tests were the mitigation that "keep[s] legitimate performance" while blocking them ([ImpossibleBench](https://arxiv.org/html/2510.20270)). `block-test-deletion`, `block-test-disabling` and `tasks-guard` implement exactly that. Blitz also already has the abort path the same paper measured, as the `test-assertion-suspect` and `hard_spec` blocked reasons in `skills/_shared/loop.md`. Three gaps remain:

- **Special-casing is not caught.** Read-only tests do not stop special-casing, and LLM monitors catch only **42–65%** of cheating on realistic repos. The critic checklist should add static greps for test literals appearing in source diffs.
- **Prompts alone do not stop cheating.** METR found "do not cheat" instructions had a "nearly negligible" effect ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)), so blitz's structural controls must stay primary.
- **Stale "pass" claims are the dominant false-done failure.** One developer found 35 of 101 "tests pass" claims untrue, mostly because the tests passed and then more editing followed ([dev.to Eiberger](https://dev.to/vinzenz_eiberger/i-checked-101-tests-pass-claims-from-my-ai-coding-agents-35-werent-true-h6n)). Recommendation 7 adds a rule that the last `verify[]` run must postdate the last edit.

Recommendation 7 also adds the Sonnet-specific text Anthropic publishes. Sonnet 5.5 "sometimes reports a code change as done without running a check" at low effort, and Anthropic offers a verification paragraph that makes skipped checks rare "with no measurable change in task quality and only a slightly higher cost". Sonnet 5.5 at `medium` is "more likely to stop and check in with the user before it finishes", so the dev contract needs a "keep working until done" clause. Sonnet also "tends to add tests, documentation, and small supporting files… even when you don't ask", which runs against blitz's surgical-scope rule and should be named in the dev contract ([Prompting Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). These instructions belong in the Sonnet `dev` prompt. They do not belong in Opus orchestrator prompts, where the Opus 5 over-verification warning applies.

## Unattended loops need a circuit breaker, thin ticks and a fresh context

Blitz's loop design follows the consensus pattern. Anthropic's long-running harness, Huntley's Ralph loop and Cursor's planner/worker/judge system all converge on the same elements: fresh context per iteration, one task per iteration, machine-edited JSON state, a progress log, git commits and an independent judge ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Cursor](https://cursor.com/blog/scaling-agents)). Where blitz lags is runaway protection. A background subagent once repeated an identical `npm install` **300+ times over 4.6 hours, consuming about 27M tokens** ([#15909](https://github.com/anthropics/claude-code/issues/15909)). A Stop hook that blocked while background subagents ran forced **100+ idle turns over about 50 minutes** and used up a session quota ([#55754](https://github.com/anthropics/claude-code/issues/55754)).

`stop-gate.sh` already respects `stop_hook_active`, has terminal markers and caps its own blocks. It does not read the Stop payload's `background_tasks`, which is the documented workaround for the second incident ([issue #93672](https://github.com/anthropics/claude-code/issues/93672)). Recommendation 8 adds that check. It also corrects `loop.reference.md`, which says the platform cap is 5 blocks under `CLAUDE_STOP_HOOK_BLOCK_CAP`. The docs now say Claude Code ends the turn "after eight consecutive stop-hook continuations" under `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` ([Hooks](https://code.claude.com/docs/en/hooks)). Blitz's `max_blocks: 4` still exhausts first, so behavior is unchanged.

Across ticks, `next --loop` lists `circuit-breaker` tasks and moves on, but nothing stops the loop itself when it is spinning. The frankbria Ralph implementation opens its breaker after **3 loops with no file changes or commits, or 5 loops with the same error**. It also caps calls and tokens per hour ([ralph-claude-code](https://raw.githubusercontent.com/frankbria/ralph-claude-code/main/README.md)). Recommendation 9 adds an equivalent to `next-state.sh`: compare the last N tick commits and blocked reasons, and emit `LOOP_ESCALATE` with a "no progress" reason. It also adds a per-tick turn and token budget. Opus 5.5 makes this more pressing, because in unattended loops it "ends some turns with a text-only progress report". Anthropic advises treating that as a report rather than completion, with a cap of 2–3 automatic continuations ([Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). Blitz's terminal markers and `max_blocks` already fit that advice.

The economics favor keeping each tick small. A scheduled task "fires on its interval even while the session is idle, sending your full context each time" ([Costs](https://code.claude.com/docs/en/costs)). Opus 5.5 and Sonnet 5.5 auto-compact at about **967K tokens** by default ([Model config](https://code.claude.com/docs/en/model-config)). Context-rot studies show degradation long before that point, and Claude showed the largest gap between focused and full prompts on LongMemEval ([Chroma](https://www.trychroma.com/research/context-rot)), though none of these studies tested 5.x models. Anthropic's own advice for multi-window work is to start "a brand new context window rather than using compaction", because current models are "extremely effective at discovering state from the local filesystem" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Blitz should document a `claude -p` per tick, or a Routine (cloud, 1h minimum, fresh clone ([Routines](https://code.claude.com/docs/en/routines))), as the preferred form of durable unattended runs. When a same-session `/loop` is used, it should recommend an `autoCompactWindow` of roughly 200–300K on that main thread. Agents should still leave `autoCompactWindow` unset, as 3.10.0 decided.

Blitz's caching choices are sound but have limits that are not yet documented. On 5.5 models, a 1h write costs 2x base against 1.25x for 5m, and reads cost 0.05x ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). A critic re-spawned once after a 6–59 minute gap covers the 1h premium, so `subagentPromptCacheTtl: 1h` is justified. Claude Code's cache is "effectively scoped to one machine and directory", and a subagent's first request "doesn't read the parent's cache" ([How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)). Worktree-isolated parallel `dev` agents therefore do not share a prefix with each other. `/usage` covers only the main conversation, so blitz's per-task cost claims need `-p` JSON or OTel evidence (P2 telemetry). Separately, the 5,000-token skill cap is correct, but Anthropic adds a **combined 25,000-token re-attach pool**, filled starting from the most recently invoked skill, and "older skills can be dropped entirely" ([Skills](https://code.claude.com/docs/en/skills)). A long `next --loop` session that chains more than five large skills will lose the oldest ones after compaction. This belongs beside the 5K rule in the skill authoring contract.

## What to leave alone, and what to drop

**Agent teams should stay off.** They "use approximately 7x more tokens than standard sessions when teammates run in plan mode" ([Costs](https://code.claude.com/docs/en/costs)). They drop `skills` preload and cannot resume in-process teammates. The docs say that "for sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective" ([Agent teams](https://code.claude.com/docs/en/agent-teams)). Practitioners report the same thing: token use "scales linearly with team size", and teams pay off for review and competing hypotheses, not routine builds ([Push To Prod](https://getpushtoprod.substack.com/p/30-tips-for-claude-code-agent-teams)). Blitz's wave cap of 4 sits inside the 3–5 range that both Anthropic and practitioners name ([dev.to jcamarate](https://dev.to/jcamarate/why-20-claude-code-instances-break-down-and-what-to-do-2i5j)), and it should stay.

**Mods are a P2 add-on, not a replacement.** An `agent.spawn` handler could enforce model and effort per `blitz:*` type, including workflow agents. `tool.check` with `agentId` could make the critic read-only without parsing strings, and `$.ui.status` could show wave progress ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). However, mods are unsandboxed JS that users must trust. They require 2.1.287 or later, and they disappear under `--safe-mode` and `disableAllHooks`. The shell hooks must remain the portable baseline.

Several stale statements should be retired (recommendation 11). `agents.md` §1.4 says "Subagents cannot spawn subagents". The platform now allows nesting "up to three layers below the main conversation" ([Sub-agents](https://code.claude.com/docs/en/sub-agents)), so blitz should present this as its own policy, optionally enforced with `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`. The `skill_doctor` floor of 2.1.252 in `compat.json` conflicts with the changelog's 2.1.261 ([CL 2.1.261](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)). The research notes and the coordinator's spot-check disagree on which older section first lists it, so this is low-priority cleanup. Finally, the evidence gives no reason to add persona swarms, "self-learning" memory, or heavy spec ceremony. Those are the features with the most documented complaints and the least measurement among comparable projects. Examples include ruflo's self-audit, which marked core features as stubs ([AlphaSignal](https://alphasignalai.substack.com/p/how-ruflo-turns-claude-code-into)), and spec-kit and Kiro producing "a false sense of control" ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

## Conclusion

The research changes the question blitz should ask about itself. It is no longer "which new platform features should we use", because the 3.10.0 adoption of per-spawn effort, labelled fan-outs and the 5.5 table was largely right. The question is now "which of our guarantees fail silently". The evidence identifies three silent failures. Guards let calls through when they crash. A declared floor sits below features already in use. An external veto blocks good work on roughly 30%-precision signals. Each is cheap to fix, and each fix turns an implied guarantee into a real one.

Blitz's most distinctive bet, hook-enforced and script-written task state with deterministic verify commands, is also the bet the anti-cheating literature supports most strongly. It deserves an eval that proves it: a contradictory-spec canary that should end in `test-assertion-suspect`, and known-good fixtures that measure how often the critic blocks sound work. Without those measurements, blitz cannot answer Anthropic's warning that every harness component "encodes an assumption about what the model can't do on its own", and that such assumptions expire as models improve. With them, the next round of model releases becomes an ablation run rather than a guess.
