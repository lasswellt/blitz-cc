# Security, supply-chain and hook reliability for Claude Code plugins (blitz review input, as of 2026-10-10)

Scope: documented attacks on Claude Code / MCP / skills / plugins; Anthropic's own controls; prompt-injection defense research; hook reliability (fail-open/closed, timeouts, Windows, mods); skill and plugin supply chain. Concrete blitz recommendations live in the Inferences subsections. Every source is dated where the date could be determined. Anthropic docs pages (code.claude.com) are undated live docs read on 2026-10-10 and reflect Claude Code through roughly v2.1.295.

Local check of blitz (read 2026-10-10, not a web source): `hooks/hooks.json` sets `timeout` values on hooks but no `onFailure` key on any hook. `hooks/scripts/block-destructive-sql.sh` parses input with `jq ... 2>/dev/null || echo ""` and then `[[ -z "$CMD" ]] && exit 0`, so a missing or broken `jq` makes the guard allow everything. `critic-external.sh` runs codex with `exec --sandbox read-only --ephemeral`, copilot without `--allow-all-tools`, and agy with a narrow allow-list instead of `--dangerously-skip-permissions`. The compat floor is `cc_min: 2.1.271`.

## Documented attacks and vulnerabilities (repo-file injection, malicious plugins/marketplaces, hook abuse, Plugin4Shell, CVEs, lethal trifecta, exfiltration via allowed domains)

### Takeaway
The real-world record from 2025–2026 shows one recurring pattern: repository-controlled or marketplace-controlled configuration ran code, or sent credentials out, before the user's trust decision took effect. That covered hooks, `.mcp.json`, `ANTHROPIC_BASE_URL`, and plugin commit pins (Plugin4Shell). All known Claude Code instances are patched. The structural risk remains in two places: the lethal trifecta (private data, untrusted content, outbound channel), and allowlisted domains that cannot stop exfiltration.

### Cited Findings
- **CVE-2025-59536 (hooks and MCP consent bypass, Claude Code).** A project `.claude/settings.json` could define hooks, such as SessionStart, that ran shell commands from an untrusted repo without explicit approval. Separately, `enableAllProjectMcpServers` / `enabledMcpjsonServers` in repo settings auto-approved `.mcp.json` servers before the user could read the trust dialog. Timeline: hooks issue reported Jul 21 2025 and fixed Aug 26 2025 (GHSA-ph6w-f82w-28w6); MCP bypass reported Sep 3 and fixed Sep 22 2025; CVE published Oct 3 2025. — [Check Point Research, 2026-02-25](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- **CVE-2026-21852 (API key exfiltration).** A repository could set `ANTHROPIC_BASE_URL` in `.claude/settings.json`. Claude Code then sent requests, with the user's API key in the authorization header, to the attacker before the trust dialog was accepted. Reported Oct 28 2025, fixed Dec 28 2025, CVE published Jan 21 2026. Fix: no network requests before trust is accepted. — [Check Point Research, 2026-02-25](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- CVSS for CVE-2025-59536 is reported as 8.7. Secondary sources disagree on CVE-2026-21852 (5.3 vs 7.5). Fixed-version claims of 1.0.111 and 2.0.65 come only from secondary sources. — search summary of [MintMCP blog](https://www.mintmcp.com/blog/claude-code-cve) and [borncity, 2026-03-02](https://borncity.com/win/2026/03/02/vulnerabilities-cve-2025-59536-cve-2026-21852-in-anthropic-claude-code/) (search snippets only, not fetched)
- **Plugin4Shell (commit-pin bypass, zero-click via auto-update).** Air Security (Or Nevo, Dor Granat, Niv Hoffman) published on 2026-09-17. An attacker who controls a plugin repo creates a default branch named after the pinned 40-hex commit SHA, and git resolves the branch ahead of the commit, so the agent installs different code than the reviewed commit. Background auto-update makes the attack zero-click. Fixed in Claude Code 2.1.179 and Codex 0.146.0. Copilot is unpatched, with GitHub disputing the attack. Gemini CLI will not be patched (FETCH_HEAD variant). No CVE had been assigned and no in-the-wild exploitation was known as of 2026-09-21. The main exposure is non-GitHub marketplaces, because GitHub rejects hash-shaped branch names. — [hard2bit, 2026-09-21](https://hard2bit.com/en/blog/plugin4shell-commit-pinning-bypass-ai-coding-agent-plugins-claude-code-codex-copilot-gemini/); corroborated by [cybersecuritynews](https://cybersecuritynews.com/plugin4shell-zero-click-rce/) (search snippet only)
- Plugin4Shell mitigations: restrict marketplaces to GitHub or to hosts that reject hash-shaped branch names; disable plugin auto-update on managed machines; compare the resolved commit after checkout with the pin; use short-lived git tokens; isolate projects that use third-party plugins in containers or VMs. — [hard2bit, 2026-09-21](https://hard2bit.com/en/blog/plugin4shell-commit-pinning-bypass-ai-coding-agent-plugins-claude-code-codex-copilot-gemini/)
- **MCP tool poisoning, rug pulls and cross-server shadowing.** Hidden instructions in tool descriptions made Cursor read `~/.cursor/mcp.json` and `~/.ssh/id_rsa` and pass them through a parameter. Servers can change descriptions after approval ("rug pull"). A malicious server's description redirected a trusted `send_email` tool to an attacker address. Mitigations: pin servers and tools and hash their descriptions, show full descriptions to users, enforce cross-server data-flow boundaries. — [Invariant Labs, 2025-04-01](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- **CVE-2025-6514 (mcp-remote).** OS command injection when connecting to an untrusted MCP server via a crafted OAuth `authorization_endpoint`. Affects versions 0.0.5–0.1.15, fixed in 0.1.16, CVSS 9.6, found by JFrog. — [OSV CVE-2025-6514](https://osv.dev/vulnerability/CVE-2025-6514) (search result summary; JFrog primary not fetched)
- **Gemini CLI (Tracebit).** Prompt injection hidden in ordinary project files (README/GEMINI.md) chained with weak allowlist parsing: a command starting with an allowlisted `grep`, followed by whitespace, then `; env | curl ...`, ran silently. Reported 2025-06-27, fixed in v0.1.14 on 2025-07-25. A later and separate `--yolo` allowlist bypass was rated CVSS 10 (GHSA-wpqr-6v78-jr5g). — [BleepingComputer](https://bleepingcomputer.com/news/security/flaw-in-gemini-cli-ai-coding-assistant-allowed-stealthy-code-execution) and [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-gemini-cli-rce-cvss10-ai-tool-security-202/) (search snippets only)
- **Lethal trifecta.** Access to private data, exposure to untrusted content, and the ability to communicate externally together let an attacker exfiltrate. Exfil vectors include HTTP requests, image loads from external URLs, clickable links, and write actions such as PRs (the GitHub MCP exploit). Willison: "95% is a failing grade"; guardrail products cannot be trusted. Once an agent has ingested untrusted input, constrain it so that input cannot trigger consequential actions. — [Simon Willison, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **Exfiltration via allowed domains.** Anthropic's sandbox docs warn that "allowing broad domains such as `github.com` can create paths for data exfiltration". The proxy decides from the client-supplied hostname without inspecting TLS, so "domain fronting or similar techniques" can reach hosts outside the allowlist. — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- **OWASP Top 10 for Agentic Applications 2026.** Published 2025-12-09, items ASI01–ASI10, covering goal and plan hijack, tool misuse, identity and privilege, supply chain, unexpected code execution, memory and context poisoning, insecure inter-agent communication, cascading failures, human-agent trust exploitation, and rogue agents. It cites EchoLeak and a coding agent that deleted a production DB during a code freeze. — [OWASP GenAI](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026) (search summary; page not fetched)

### Inferences
- The external critic in blitz forms a trifecta. It holds private data (the repo diff), takes in untrusted content (diff text written by an agent, possibly carrying injected repo content), and has an outbound channel (third-party CLIs on vendor clouds). Sending the diff out is itself the exfiltration path. The safeguards should be: opt-in per repo, a secret scan of the diff before it leaves (gitleaks or the existing secret regexes), redaction of `.env`-like hunks, and a visible list of where data goes.
- The two Check Point CVEs and Plugin4Shell are the exact class blitz itself relies on: plugin hooks run with full user privileges and outside the sandbox. blitz should publish its own threat model saying that "installing blitz = trusting ~40 bash scripts as you", and pin its marketplace to GitHub.
- `.cc-sessions/` records that later get injected into SubagentStart context are a memory-poisoning vector (OWASP ASI06-class, and Snyk saw memory-file poisoning in the wild). blitz is right to treat them as untrusted. The defense is structural: wrap them as data, strip control sequences, apply length caps. The regex scan is only a tripwire.

### Gaps
- Primary Anthropic GHSA text and exact fixed versions for CVE-2025-59536 and CVE-2026-21852 were not fetched. Version numbers are secondary claims.
- No CVE was found that specifically concerns `!`-prefixed shell injection lines in skills. Whether `!` lines run in an untrusted folder under `-p` is covered only indirectly (the "What runs before you trust a folder" table lists project skill hooks and `allowed-tools`, not `!` lines).
- The primary Air Security report was not fetched; dates come from hard2bit coverage.

## Anthropic's security guidance (sandboxing, auto mode classifier, permission rules, managed settings, devcontainers, egress, blockReadsOutsideWorkingDirectories)

### Takeaway
Anthropic's model has layers: deny-first permission rules, an OS sandbox for Bash only, an auto-mode classifier that never sees tool results, protected paths, workspace trust, and managed settings as the only tier that cannot be overridden. The docs state plainly that hooks, MCP servers, plugin monitors and mods run outside the sandbox with full user access, and that the egress proxy does not inspect TLS.

### Cited Findings
- Permission rules are evaluated deny → ask → allow. "An allow rule can't carve an exception out of a deny rule." A deny at any scope beats an allow at any other. — [Claude Code docs: Permissions](https://code.claude.com/docs/en/permissions)
- PreToolUse hook decisions don't bypass permission rules: a matching deny still blocks and a matching ask still prompts even when a hook returns "allow". A hook that exits 2 blocks before rules are evaluated, so it overrides allow rules. — [Permissions](https://code.claude.com/docs/en/permissions)
- Bash argument patterns are fragile. `Bash(curl http://github.com/ *)` misses option reordering, protocol changes, redirects and variables. A deny rule doesn't match the same program by path or inside `sh -c`. Pair it with the sandbox network allowlist. — [Permissions](https://code.claude.com/docs/en/permissions)
- `permissions.blockReadsOutsideWorkingDirectories` makes file tools refuse paths outside the working directories in every mode. Auto mode offers to turn it on at the first out-of-tree read. — [Permissions](https://code.claude.com/docs/en/permissions)
- **What runs before trust.** In `claude -p` / SDK runs (never trusted), project hooks in settings files, the `env` block, `apiKeyHelper`, a project skill's hooks and its `allowed-tools` all run. `.mcp.json` servers connect "without asking, approved or not". Hardening for untrusted repos: `--setting-sources user`, `--bare`, or `--settings '{"disableAllHooks": true}'`. A user-level `disableAllHooks` alone is insufficient because project settings take precedence. — [Permissions](https://code.claude.com/docs/en/permissions)
- **The sandbox covers shell commands only.** "Claude's file tools, MCP servers, and hooks run outside it". Command hooks, local MCP servers, plugin monitors, LSP servers, the status line and `apiKeyHelper` "run with your full access". Native Windows runs commands unsandboxed; WSL2 is required. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Sandbox hardening knobs: `failIfUnavailable` (otherwise it silently runs unsandboxed when deps are missing), `allowUnsandboxedCommands: false` (disables the `dangerouslyDisableSandbox` retry), `strictAllowlist` (v2.1.219+, ignored in repo settings), `allowManagedDomainsOnly`, and an ask rule on `Bash(dangerouslyDisableSandbox:true)`. Inside writable dirs the sandbox still denies writes to `.claude` settings, skills, agents, hooks, `.mcp.json`, `.claude/workflows`, shell rc files and `.git/hooks`. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Sandbox caveats: `excludedCommands` that cover an interpreter or a tool acting on a file in the repo let Claude write that file and run it unsandboxed. `enableWeakerNestedSandbox` (Docker) "considerably weakens security". Effective sandboxing needs both filesystem and network isolation. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- **The auto mode classifier sees** user messages, non-read-only tool calls and CLAUDE.md. "Tool results are stripped… so hostile content in a file or web page can't manipulate the classifier directly". A separate server-side probe scans incoming tool results. A PostToolUse hook can annotate results via `classifierContext` (v2.1.236+). Auto mode is the default starting mode from v2.1.283. — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- The classifier blocks by default, among other things: force push; `git reset --hard` and similar; secrets leaving the repo; disabling CI checks; "Launching an autonomous agent loop that runs without human approval or a sandbox… including running a third-party agent or eval harness with isolation and per-action approval disabled, such as a runner started with `--yes-always`"; commenting out security-guarding tests; repointing API base URLs; writing to session transcripts (v2.1.205+). — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- **Protected paths** (never auto-approved outside bypass): `.git`, `.claude` (with exceptions), `.vscode`, `.husky`, `.devcontainer`, shell rc files, `.npmrc`, `.pre-commit-config.yaml`, lefthook files, `.mcp.json`, `.claude.json`, and any `--plugin-dir` directory. `rm` on critical paths can't be allowed by any rule or hook. — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- General guidance: avoid piping untrusted content to Claude; use VMs for scripts and web-facing tool calls; run the whole process in the sandbox runtime or a dev container for more isolation; use managed settings; audit config changes with `ConfigChange` hooks; monitor via OpenTelemetry. WebFetch returns a summary from a separate model, not the raw page. — [Claude Code docs: Security](https://code.claude.com/docs/en/security)
- In cloud sessions, GitHub credentials never enter the VM. A proxy attaches them server-side and rejects branch deletions and tag pushes. — [Security](https://code.claude.com/docs/en/security)

### Inferences
- blitz's `block-destructive-sql`, `block-destructive-git` and `block-no-verify` guards duplicate parts of what the auto-mode classifier and protected paths already do (force push, `reset --hard`, critical-path rm). They still matter in Manual/acceptEdits/bypass modes and as deterministic layers. Recommendation: document them as defense-in-depth, and lean on `permissions.deny` and the sandbox for anything that must hold, since regex on command text has the same bypass surface the docs warn about (`sh -c`, variables, paths).
- The critic invokes third-party agent CLIs headlessly. The auto-mode classifier is explicitly tuned to block third-party agents run with approval or isolation disabled. blitz's existing choices (codex `--sandbox read-only`, no copilot `--allow-all-tools`, an agy allow-list) match that rule. blitz should keep them, add a test asserting no `--yolo`, `--dangerously-*` or `--yes-always` flags, and note that agy's `--sandbox` "blocks neither writes nor network" (blitz's own comment), which leaves agy the weakest provider.
- blitz should recommend, not require, a hardened profile: `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, `blockReadsOutsideWorkingDirectories`, and denies on `curl`/`wget` with WebFetch domain allows. It should also ship a `--bare`/`--setting-sources user` recipe for running blitz loops headlessly on repos it didn't write.
- blitz's PostToolUse validators could emit `classifierContext` to tell the auto-mode classifier when a result came from untrusted content (for example, critic output). That is a cheap, Anthropic-supported spotlighting channel.

### Gaps
- The `blockReadsOutsideWorkingDirectories` settings-reference entry (default value, managed-only status) was not fetched in detail.
- The devcontainer reference firewall script was not reviewed.

## Prompt-injection defense research (CaMeL, design patterns, spotlighting, dual LLM) and applicability to a plugin

### Takeaway
The only defenses with provable properties are architectural: control and data flow separation (CaMeL), plan-then-execute, the dual LLM, and context minimization. Probabilistic defenses such as spotlighting and classifiers reduce attack success rates but do not eliminate them. A plugin cannot rebuild Claude Code's control loop. It can apply the patterns at its own boundaries: critics, subagent context injection, and session records.

### Cited Findings
- **Six patterns** (Beurer-Kellner, Tramèr, Debenedetti et al., arXiv 2506.08837): Action-Selector; Plan-Then-Execute; LLM Map-Reduce (sub-agents process untrusted items and return constrained results); Dual LLM (a privileged LLM drives a quarantined LLM that returns symbolic variables); Code-Then-Execute (a DSL with taint tracking); Context-Minimization. In the coding-agent case study, the agent sees only formal API descriptions, which reduces utility but forces injections to survive strict formatting. — [Simon Willison summary, 2025-06-13](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/); [arXiv 2506.08837, v1 2025-06-10, v3 2025-06-27](https://arxiv.org/abs/2506.08837)
- **CaMeL** (Debenedetti, Shumailov, Carlini, Tramèr et al.) builds a protective system layer that separates control and data flow, so untrusted data can't affect program flow. Capabilities block private data leaking over unauthorized flows. On AgentDojo it solved 77% of tasks with provable security, vs 84% undefended. — [arXiv 2503.18813, v1 2025-03-24, v2 2025-06-24](https://arxiv.org/abs/2503.18813)
- **Spotlighting** (Hines et al., Microsoft) transforms input so the model can track provenance. It cut attack success rates from >50% to <2% on GPT-family models with minimal task impact. — [arXiv 2403.14720, 2024-03-20](https://arxiv.org/abs/2403.14720)
- Willison originated the Dual LLM pattern (April 2023) and calls CaMeL the first credible proposal. He stays skeptical of guardrail and detection approaches. — [Willison, 2025-06-13](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/); [Willison, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Claude Code itself applies context minimization (WebFetch returns a separate model's summary), classifier isolation (tool results stripped from classifier input), and a server-side probe on tool results. — [Security](https://code.claude.com/docs/en/security); [Permission modes](https://code.claude.com/docs/en/permission-modes)

### Inferences
- How the patterns map onto blitz:
  - **Map-Reduce / Dual LLM at the critic.** Critic output is untrusted (a third-party model that read possibly injected diff text). Constrain it to a schema (findings JSON with severity, file, line, and a capped-length summary). Validate it with `jq`, and never splice raw critic prose into the main agent's instructions. Treat it as data in a fenced, labeled block (spotlighting).
  - **Context-Minimization at SubagentStart.** Inject only the fields a subagent needs from `.cc-sessions/`. Escape them, length-cap them, and label them as untrusted data. The regex scan for injection phrases is a tripwire with a known bypass rate, not a boundary.
  - **Plan-Then-Execute** already fits `tasks.json`, which is written only via `scripts/tasks.sh` and enforced by `tasks-guard.sh`. Here, tool outputs can't add tasks unless they pass the writer. Keep the guard fail-closed (see below).
  - `omitClaudeMd` on critics is a good context-minimization step. It keeps repo-controlled instructions out of the critic.
- Do not market regex scanning as prevention. In blitz docs, call it detection or telemetry, consistent with Willison's "95% is failing".

### Gaps
- No published evaluation was found of spotlighting or CaMeL specifically on Claude models or on coding-agent benchmarks beyond the AgentDojo numbers.

## Hook reliability: fail-open vs fail-closed, performance, Windows, timeouts; how mods change the picture

### Takeaway
Command hooks fail open by default. A crash, a non-0/2 exit, an invalid JSON response, a missing binary, or a timeout on PreToolUse lets the tool call through. v2.1.295 added `onFailure: "block"` to make individual hooks fail closed. Mods (v2.1.286/287+) run in-process and can override non-managed PreToolUse blocks and ask rules. Outside managed or Team/Enterprise setups they can even override deny rules. So a blitz guard hook is no longer the last word on a machine with user-installed mods.

### Cited Findings
- **Exit semantics.** Exit 0 = success. Exit 2 = blocking (stderr is the reason). "Any other exit code, crash, or can't start" = non-blocking error and "the action proceeds". Invalid JSON on exit 0 is non-blocking. The docs say "If your hook is meant to enforce a policy, use exit 2." Silence isn't approval. — [Claude Code docs: Hooks](https://code.claude.com/docs/en/hooks)
- **Timeouts.** Defaults are 600s for command/http/mcp_tool, 30s for prompt, 60s for agent, and 30s on UserPromptSubmit. "A timed-out command… hook on PreToolUse doesn't block the tool call". The timeout isn't enforced on `async: true` hooks. — [Hooks](https://code.claude.com/docs/en/hooks)
- **`onFailure: "block"` (v2.1.295+)** on command/http hooks blocks on can't-start, any exit other than 0/2, non-2xx, timeout, or invalid output. It has no effect on Stop, SubagentStop, TaskCompleted, TeammateIdle or async hooks. — [Hooks](https://code.claude.com/docs/en/hooks)
- Exit 2 has no effect on PostToolUse, PermissionRequest, Notification or StopFailure. PermissionRequest must deny via the `decision` object. — [Hooks](https://code.claude.com/docs/en/hooks)
- All matching hooks run in parallel. Identical handlers across settings files are deduped, but a plugin's copy stays separate. The `if` filter is best-effort: "use the permission system rather than a hook to enforce a hard allow or deny." — [Hooks](https://code.claude.com/docs/en/hooks)
- **Windows.** `shell` is bash, or PowerShell on Windows when Git Bash is absent. Exec form (`args`) needs a real `.exe` on Windows (`.cmd`/`.bat` shims fail). Hooks have no TTY. — [Hooks](https://code.claude.com/docs/en/hooks)
- `additionalContext`, `systemMessage` and `initialUserMessage` are capped at 10,000 chars. Overflow goes to a file Claude isn't asked to read. — [Hooks](https://code.claude.com/docs/en/hooks)
- Project skill hooks register on invocation even in `-p` in an untrusted folder. Project subagent frontmatter hooks need trust (v2.1.218+). — [Hooks](https://code.claude.com/docs/en/hooks)
- `disableAllHooks` resolves by precedence, so a project's `false` overrides a user's `true`. `allowManagedHooksOnly` blocks user, project and plugin hooks except force-enabled managed plugins. — [Hooks](https://code.claude.com/docs/en/hooks)
- **Mods.** A plugin's in-process JS hooks module. Mods are on by default from v2.1.287 (terminal) and v2.1.286 (Desktop). They "aren't sandboxed". A mod can read secrets, see every prompt and tool call, rewrite them, approve calls, and spend usage via `$.model.complete`. Processes it starts run outside the sandbox. Review a mod with `claude plugin validate` (`hooks:` and `calls:` lines). — [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)
- **Mod precedence.** A mod handling `tool.check` answers after rules and PreToolUse hooks and "can replace theirs". It can approve ask-rule prompts, approve calls blocked by a non-managed PreToolUse hook, and skip the auto-mode classifier. Deny rules hold over mods only with managed settings or a Team/Enterprise login (the `sec-default` guard), and `allowModsToOverrideDenyRules` can relax that. Elsewhere, "the mod can approve a call that a deny rule refuses." — [Permissions](https://code.claude.com/docs/en/permissions); [Mods admin](https://code.claude.com/docs/en/plugins/mods/admin)
- **Mod ordering.** Managed PreToolUse hooks run before any mod, and run again if a mod rewrites the call. "PreToolUse hooks from other settings files and from plugins run after the last mod, so a mod that returns its own result in place of running the tool keeps those from running." — [Mods admin](https://code.claude.com/docs/en/plugins/mods/admin)
- Mod failure modes: a `plugin.register` hook that throws or times out is skipped, so it fails open, unless `.catch` returns a refusal. If the hooks worker crashes three times, all non-built-in mods unload for the session. The built-in `sec-default` guard fails closed if it can't read managed settings. — [Mods admin](https://code.claude.com/docs/en/plugins/mods/admin)

### Inferences
- **blitz-specific fail-open bug class.** Guards such as `block-destructive-sql.sh` do `jq … || echo ""` and then `exit 0` on empty input. A missing `jq`, malformed stdin, or a `set -e` abort (exit 1) silently allows the call. blitz's `_lib/common.sh` already notes that exit 1 is fail-open. Recommendations:
  1. Add `"onFailure": "block"` to every enforcement PreToolUse hook (`block-*`, `tasks-guard`, `pre-edit-guard`). Raise a feature floor of 2.1.295 in `compat.json` for this key, or gate it so older clients ignore it.
  2. In each guard, treat a parse failure as a block (exit 2 with a clear reason) rather than as empty input. Install an `ERR`/`EXIT` trap that converts unexpected exits into exit 2 for enforcement hooks only.
  3. Verify `jq` in `startup-validate.sh` and refuse loudly when it is missing.
  4. Keep advisory hooks (formatters, telemetry, context injection) fail-open so a broken helper doesn't brick sessions.
- **Timeouts.** blitz's 600s hook (likely the critic) is fine only if async or off the PreToolUse path. Any PreToolUse guard timeout is fail-open without `onFailure`. Keep guards at ≤10s with no network.
- **Stop gate.** `onFailure` doesn't apply to Stop, so a crashing `stop-gate.sh` just lets the turn end. blitz should make the gate exit 2 explicitly on internal error when a gate.json is in force, and include a loop-breaker (cap re-prompts) to avoid infinite Stop loops.
- **Windows.** Bash-only hooks fail as "can't start" on Windows without Git Bash, which is fail-open. blitz should either declare Windows unsupported (WSL2 only, matching the sandbox) or have `startup-validate` detect it and warn.
- **Mods change the trust model.** On a personal machine with any user-installed mod handling `tool.check`, blitz's PreToolUse blocks can be overridden, and even deny rules can be. blitz cannot prevent this, but should (a) document it, (b) optionally detect active mods at SessionStart (for example from `/plugin` output or the debug log) and warn, and (c) consider shipping its guard logic as a mod later. A mod that is not org-managed still runs in the user tier, so this does not gain managed precedence. A blitz mod could also use `$.model.complete` for critics without spawning third-party CLIs.

### Gaps
- No published benchmark of hook latency overhead was found. Performance guidance is limited to timeouts and parallel execution.
- The `mods/events` page ("Handle a hook that fails", default per-hook time limits for mods) was not fetched, so exact mod timeout values are unknown.

## Supply chain for skills and plugins: scanners, signing, marketplace policies

### Takeaway
The skills ecosystem has a measured malware problem: 13.4% of ~4k public skills had critical issues in Feb 2026. Claude Code has no publisher signing. Its integrity controls are reserved marketplace names, commit-SHA pins in the community catalog, `sha256` pins for archive sources, the Plugin4Shell fix, and managed marketplace allowlists. The trust warning states that Anthropic "cannot verify" plugins.

### Cited Findings
- **Snyk ToxicSkills.** 3,984 skills from ClawHub and skills.sh scanned; 534 (13.4%) had critical issues and 1,467 (36.82%) had any flaw; 76 confirmed malicious payloads. 91% of malicious skills combined prompt injection with malware, and 100% had malicious code patterns. Techniques seen: `curl | bash` remote payloads (benign at publish, swapped later), base64/Unicode-obfuscated exfil, password-protected ZIPs, systemd persistence, and memory-file poisoning (`SOUL.md`, `MEMORY.md`). The scanner is `uvx mcp-scan@latest --skills`, built on 8 policy categories. — [Snyk, 2026-02-05](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)
- **What a Claude Code plugin can run:** hooks, monitors (background commands at start, reload, or first skill run), mods, MCP and LSP servers, and a `bin/` directory added to the Bash tool's PATH. Skills, commands and agents enter context as instructions. With auto-update on, "the files you reviewed can change on disk". — [Plugin security](https://code.claude.com/docs/en/plugins/security)
- **Marketplace tiers.** Official and community names are accepted only from `github.com/anthropics/`; anything else claiming them is refused ("Marketplace is registered from an untrusted source"). The community catalog pins nearly every plugin to a commit SHA and refuses other commits. `archive` sources with a `sha256` pin fail closed on mismatch. — [Plugin security](https://code.claude.com/docs/en/plugins/security)
- **Review workflow:** `claude plugin marketplace list` (source), the `/plugin` "Will install" pane, reading `hooks/hooks.json`, `.mcp.json` and `bin/`, `claude --plugin-dir <dir> plugin details <name>` for a component inventory, and `claude plugin validate` for mods. — [Plugin security](https://code.claude.com/docs/en/plugins/security); [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)
- **Org controls:** marketplace allow and block lists (`strictKnownMarketplaces`), force-enable, `disableSideloadFlags` (rejects `--plugin-dir`, `--plugin-url`, `--agents`, `--mcp-config`), `allowManagedHooksOnly`, `pluginTrustMessage`, and update policy. Plugins from GitHub, git, URL or npm sources always count as user-tier, even when force-enabled. — [Plugin security](https://code.claude.com/docs/en/plugins/security); [Mods admin](https://code.claude.com/docs/en/plugins/mods/admin)
- Anthropic reviews Directory connectors against listing criteria but "does not security-audit or manage any MCP server." — [Security](https://code.claude.com/docs/en/security)

### Inferences
- blitz as a publisher should:
  1. Ship from GitHub only, which avoids the Plugin4Shell host class, and publish release tags with a stable SHA. If an `archive` source is offered, publish the `sha256`.
  2. Avoid any `curl | bash` or runtime-fetched instructions in skills and hooks (Snyk's top malicious pattern). Make sure `!` injection lines in skills only run local, read-only commands with fixed arguments. They run with user privileges, and project skill hooks run even in untrusted `-p` sessions.
  3. Run `mcp-scan --skills` (or an equivalent) on blitz's own `skills/` in CI and publish the result, as a trust signal and to catch regressions in `!` lines.
  4. Add a SECURITY.md threat model that enumerates TB-1..TB-5 and maps them to the OWASP ASI IDs: ASI04 supply chain, ASI06 memory poisoning (`.cc-sessions`), ASI07 inter-agent communication (critic and subagents), and ASI05 code execution (hooks and `!` lines).
  5. Document that blitz's `bin/` entries, if any, are on the Bash PATH and can shadow system tools. Avoid generic names.
- Guidance for blitz users: pin the marketplace, disable auto-update for third-party marketplaces on sensitive machines, and review hook diffs on update. Session records and `docs/plans/*/tasks.json` in a cloned repo should be treated as attacker-controlled input to blitz, since a malicious repo can ship a crafted `.cc-sessions/` or `tasks.json`.

### Gaps
- No evidence was found of cryptographic publisher signing for Claude Code plugins as of 2026-10-10. Integrity relies on host trust plus SHA/sha256 pins.
- Snyk's figures cover ClawHub and skills.sh, not Claude Code marketplaces specifically. No equivalent audit of Claude Code plugin marketplaces was found.
- npm-source integrity hardening and the refusal of git/folder npm sources (mentioned in the brief) were not confirmed in the pages fetched. The plugin security page documents only the reserved-name, community SHA-pin and archive sha256 checks.
